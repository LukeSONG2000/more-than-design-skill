# Web 场景验收

用于维护 skill 的行为评估，不是组件运行测试。让评估者只读 skill 和请求，先独立决策，再对照下列判断依据；不要仅匹配组件名或文档关键词。实际产品仍需交互、浏览器和辅助技术验证。

| 请求与变化 | 应观察到的决策 | 失败信号 |
|---|---|---|
| “只调整现有按钮的间距和重点色” | 在现有实现上直接调整，应用清晰层级与语义颜色 | 要求业务问卷、重选框架或走完整场景流程 |
| “紧凑订单后台，保留信息密度” | 用 HIG 审美改善对齐、排版和层级，保留紧凑工作流 | 强制大留白、大标题，或仅因后台身份切换 Fluent 审美 |
| “已有 Material Web 组件，优化视觉” | 保留成熟交互和无障碍，在授权范围调整视觉 | 自动换库，或认为库的默认皮肤就是不可改变的审美标准 |
| “后台里点订单修改两项，列表要留着”；再改为“手机上填写二十项” | 宽屏短编辑保留上下文；长表单/窄屏重新评估完整路由，保存草稿与返回位置 | 两种场景一律使用同尺寸 Modal |
| “删错了能恢复”；再改为“永久删除且会影响团队” | 查真实撤销能力；后者说明风险和取消确认 | 用 Undo 文案冒充数据恢复，或 Esc 触发删除 |
| “下面拉起评论，还能看视频” | 确认看和操作的差别，选择模态性、键盘与滚动行为 | 固定三档百分比，或把 Web Sheet 称为系统原生 |
| “邮箱错了告诉我”；再改为“保存成功提醒一下” | 持续字段错误与非阻断成功反馈区分 | 全部用定时消失 Toast |
| “从几万人里选同事”；再改为“选两个固定套餐之一” | 可搜索候选与简单 Radio 区分，远程请求有状态 | 都使用巨大 Select 或同一种弹窗 |
| “五万订单筛选后全选导出” | 明确查询/排序/全选/导出范围、权限与服务端能力 | 仅导出当前页面却称全部，所有数据直接塞 DOM |
| “已有 Vue 后台，增加订单页” | 延续已安装库，核对组件与业务契约 | 擅自切 React/Next.js 或安装第二套库 |
| “新建内容站，有少量交互”；再改为“已有 API 的登录后台” | 分别评价渲染、路由、部署与 UI 库，不混淆 Vite 与应用框架 | 都无条件推荐同一全栈方案 |
| “让这个网页适应手机” | 调整 Web 布局、输入和状态连续性 | 顺带改 iOS/Android/Windows 原生代码 |

记录结论为通过、部分通过或未通过，附选择理由和遗漏。缺少实际浏览器验证时不得写运行验收通过。当前专业领域库只有候选入口；不要用基础场景通过宣称全组件覆盖。
