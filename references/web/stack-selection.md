# Web 技术选型

核对日期：2026-11-03。这里给出条件式工程建议，不是厂商排名或官方“最适合”声明。已有项目先读依赖、路由、后端、组件库、部署与维护约束，不为套 skill 自动更换框架。只有选型确有必要才加载本文。

## 分清四层

| 层 | 决策内容 | 不要混淆 |
|---|---|---|
| 应用架构 / 框架 | 路由、渲染、数据边界、服务端与部署 | React/Vue 的 UI 能力不等于完整应用架构 |
| 构建工具 | 开发服务器、打包与资源处理 | Vite 是构建工具，不独自解决路由、权限和服务端数据 |
| UI / 行为库 | 组件语义、焦点、表单、主题、样式所有权 | 无样式原语、带样式库、源码分发不是同一种维护成本 |
| 领域库 | 表格、图表、富文本、地图、流程与协作 | 不为一个日期输入引入完整日程系统 |

## 从业务筛选候选

| 条件 | 优先评估 | 何时不选 / 替代 |
|---|---|---|
| 单页静态展示，交互少 | HTML/CSS + 必要脚本 | 内容规模化可评估 Astro；无需强加 SPA |
| 内容、文档、展示为主，少量互动 | Astro 与按需交互 | 大量共享客户端状态或应用流程时评估应用框架 |
| 登录后的后台，已有独立 API，SEO 不重要 | 延续 React/Vue 等现有栈，可用 Vite 构建 SPA | 必须补齐路由、权限、数据与错误处理；不要把 SPA 自动当作唯一方案 |
| 可索引的公开页面与复杂动态应用并存 | React 项目评估 Next.js；其他生态评估对应 SSR/全栈方案 | 核对部署运行时、缓存、鉴权与维护能力；不能只为“SEO”强制迁移 |
| 密集表单、表格、批量操作 | 现有 UI 库优先；React 可评估 Ant Design | 移动复杂流程、强品牌定制需核对适配和覆盖，不能直接照搬桌面组件 |
| 品牌定制明显、愿意维护组件 | React Aria / Radix 等行为原语，或 shadcn/ui 源码模式 | 需要自行承担样式整合、升级、回归；不等于开箱即得完整产品 |
| 项目已使用 Material / Fluent / Vue 组件体系 | 延续其 Web 库，核查所需组件 | 不为默认偏好引入第二套重叠组件系统 |
| 复杂表格、图表、编辑器、日程 | 按领域能力单独选成熟库 | 当前仅为评估入口，不在缺少功能/授权核验时宣称最佳库 |

技术栈不由页面色彩决定，也不由“AI 熟悉哪个”决定。UI 库提供的组件数量不是适合该业务的充分证据。

## 必要约束

从仓库与需求优先获取：页面是否可索引、内容更新频率、登录与数据敏感性、数据规模、国际化、无障碍、移动输入、离线/实时能力、后端边界、部署目标、团队维护能力、授权与预算。只问会改变决策的缺项，不一次向用户抛完整问卷。

推荐输出保持短：首选组合、满足业务的原因、主要代价、一个备选及切换条件、实施前未核验项。新版本、许可证、付费功能、浏览器支持与安全维护状态须在实际采用时重新核对；本文不固定依赖版本，也不保证某库自动符合无障碍标准。

服务端权限必须独立于 UI 禁用状态。大量数据要查服务端分页、排序、聚合与导出；SSR 不自动解决安全或性能；离线不是给页面加 Service Worker 即完成冲突同步。

## 官方来源

- [Astro 的定位](https://docs.astro.build/en/concepts/why-astro/)：内容驱动与按需交互架构。
- [Next.js 文档](https://nextjs.org/docs)：React 应用框架能力；具体部署按目标版本核查。
- [Vite Guide](https://vite.dev/guide/)：构建与开发工具定位。
- [Ant Design React](https://ant.design/docs/react/introduce/)：企业 Web 组件体系。
- [React Aria](https://react-aria.adobe.com/)：可定制样式的行为与无障碍组件。
- [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction)：行为原语。
- [shadcn/ui](https://ui.shadcn.com/docs)：组件源码与组合方式，维护责任需纳入选型。

未逐项核验的其他生态与专业库标为候选，不以此页冒充完整横向测评。跨平台桌面、原生客户端框架推荐不在本轮范围内，需用户另行批准。
